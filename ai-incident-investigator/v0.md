Tech stack — full teach, since you asked

What a framework (Gin/Echo/Chi) typically buys you: more expressive routing (path params, wildcards), a middleware ecosystem (CORS, rate limiting, compression), sometimes faster route matching via a radix tree, and request-binding/validation sugar.

- The middleware ecosystem argument matters at dozens of routes with complex cross-cutting concerns. This project has ~7 routes total across three services. A framework's middleware chaining wouldn't meaningfully simplify something that's already tiny.
- Performance — a radix-tree router's speedup over ServeMux only shows up at route counts or request rates far beyond anything here; irrelevant at this scale.
- The project-specific argument, on top of "no infra without demonstrated need": a framework is another dependency whose internals you haven't written and now have to trust — request lifecycle, middleware execution order, context handling all move partly outside code you can read end to end. Low-level decisions — you found one correctly (the client-side deadline), here are the other five

There are six total, split by which side of the connection they guard — four on the server (inbound), two on the client (outbound):

Server side (httpx/server.go, defaults shown):
1. ReadHeaderTimeout (5s) — guards against a client that opens a connection and dribbles out HTTP headers slowly, tying up a server goroutine before the request has even fully arrived.
2. ReadTimeout (15s) — same concern, one phase later: guards against a client that's slow sending the request body, after headers are done.
3. WriteTimeout (30s) — guards the opposite direction: a client (or broken network path) that's slow to read the response the server is trying to send back. Without this, the server blocks indefinitely trying to write a response nobody's draining.
4. IdleTimeout (60s) — guards a keep-alive connection sitting open with zero activity, quietly holding a file descriptor forever with nothing happening on it.

Client side (httpx/client.go):
5. Timeout (per-dependency — this is the one you found) — the overall deadline on the round trip for one outbound call. Guards against a downstream that never responds (or responds too slowly) turning into an indefinitely hanging goroutine instead of a bounded, observable failure.
6. DialTimeout (2s) — a separate, tighter timeout specifically for establishing the TCP connection itself, before any request/response exchange has even begun. Guards against an unreachable host (DNS failure, dead IP, network partition) failing fast, rather than burning the full request Timeout waiting for something that was never going to connect at all.

Low-level (context cancellation) — correct conclusion, but let's land the actual mechanical argument I was fishing for

You got the right answer, but the reasoning ("why wait longer than needed") is a convenience argument, not the realism argument I asked for. Here's the sharper version: in a real system, when your client has a 3-second timeout and calls a genuinely slow dependency, your context.WithTimeout fires at 3 seconds and your call returns immediately — regardless of what the remote server is actually doing. You have no visibility into and no control over the remote's true duration; your side unilaterally gives up at your own deadline, full stop. You never "wait 5 seconds" in reality, because nothing on your side is capable of waiting longer than its own configured timeout, no matter how slow the far end genuinely is.

So if the injected fault always slept the full configured delay regardless of context cancellation, it would be simulating something that cannot happen in a real system — that's exactly why faultx.Apply's sleep is written as select { case <-timer.C: ...; case <-ctx.Done(): return ctx.Err() }, rather than a plain time.Sleep. It makes the fake delay behave exactly like a real slow dependency interacting with a real timeout.
